Modification de la logique métier du backend - Version 2
=========================================================

Trois types de ressources à découvrir et valider :

─────────────────────────────────────────────────────────
1) service_support
─────────────────────────────────────────────────────────
   Définition :
     Services d'assistance nationaux destinés aux personnes
     (prioritairement les mineurs) confrontées à la cyberviolence
     ou à toute forme de violence, y compris hors internet.

   Priorité : services gouvernementaux ou officiellement reconnus.

   Champs requis :
     - description         : descriptif du service proposé
     - scope               : périmètre d'intervention
                             (public visé : mineurs/tous,
                              type de violence : harcèlement/cyberviolence/tous,
                              anonymat : oui/non)
     - contact_methods     : modalités de contact (téléphone, mail, formulaire...)
     - direct_link         : lien direct vers la page d'aide ou de contact
                             (accès direct au formulaire ou au numéro en cas de besoin)
     - is_governmental     : booléen indiquant si la source est gouvernementale

   Capacité LLM :
     Bonne capacité de découverte, surtout pour les services publics
     bien référencés. Nécessite un prompt précis sur le public cible
     et le territoire géographique.

─────────────────────────────────────────────────────────
2) procedure_plateforme
─────────────────────────────────────────────────────────
   Définition :
     Procédures officielles des plateformes numériques pour gérer
     les situations de cyberviolence (signalement, gestion de profil,
     blocage, suppression de contenu...).

   Périmètre :
     Inclure les réseaux sociaux classiques (Facebook, Instagram,
     TikTok, X, YouTube, Snapchat...) ET les applications de
     communication entre jeunes (Discord, WhatsApp, Telegram...).

   Champs requis :
     - description         : description de la procédure
     - platform_name       : nom de la plateforme
     - action_type         : type d'action (signalement, gestion profil,
                              suppression contenu, blocage...)
     - direct_link         : lien direct vers la page officielle d'aide

   Capacité LLM :
     Très bonne capacité pour les grandes plateformes. Penser à
     explicitement cibler les apps de dialogue (Discord, etc.)
     dans les prompts.

─────────────────────────────────────────────────────────
3) signalement_autorite
─────────────────────────────────────────────────────────
   Définition :
     Autorités légales officielles à contacter en cas de
     cyberviolence ou de violence au sens large.

   Champs requis :
     - description         : descriptif du service proposé
     - scope               : périmètre d'intervention
                             (public visé : mineurs/tous,
                              type de violence : cyberviolence/tous,
                              anonymat : oui/non)
     - contact_methods     : modalités de contact disponibles
     - phone               : numéro de téléphone direct
     - email               : adresse email de contact
     - direct_link         : lien vers le formulaire officiel de signalement

   Capacité LLM :
     Bonne capacité pour les autorités nationales connues (police,
     gendarmerie, CNIL, plateformes gouvernementales comme
     cybermalveillance.gouv.fr). Les ressources locales ou peu
     référencées seront plus difficiles à découvrir automatiquement.

🔴 PROBLÈMES CRITIQUES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. L'authentification est en réalité désactivée
────────────────────────────────────────────────
  Dans routers/sources.py, _get_auth() est défini mais jamais
  passé en Depends() :

    # Ce pattern importe la fonction mais ne l'injecte pas
    verify_admin_token = _get_auth()

  Résultat : POST /sources/validate, POST /sources/modify-and-validate,
  et tous les endpoints POST ne sont PAS protégés. N'importe qui
  peut modifier des ressources sans token.

  Correction minimale dans chaque endpoint sensible :
    @router.post("/sources/validate")
    async def validate_critical_source(request: Request, admin=Depends(verify_admin_token)):

2. allowed_fields dans modify_and_validate_source est V1
─────────────────────────────────────────────────────────
  Dans sources.py :
    allowed_fields = ["organization_name", "country_name", "phone",
                      "email", "website", "description"]

  Les champs V2 (direct_link, is_governmental, scope_*, action_type)
  sont absents → une modification V2 sera silencieusement ignorée.

🟡 PROBLÈMES IMPORTANTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

3. api_adapter.py est le nouveau monolithe
───────────────────────────────────────────
  2071 lignes — plus que le monolithe original avant découpage
  des routers. C'est désormais la dette technique principale
  du projet.

4. response_service.py (216 lignes) n'est jamais utilisé
─────────────────────────────────────────────────────────
  ResponseService, ErrorHandler, OperationLogger sont importés
  dans admin_api.py mais aucun router ne les utilise. Tous les
  routers reconstruisent manuellement {"success": False,
  "message": str(e)} à la main. La dette que ce service devait
  effacer existe toujours, en double.

5. Aucun modèle Pydantic sur les endpoints POST
────────────────────────────────────────────────
  Tous les handlers font data = await request.json() suivi de
  data.get("field"). Conséquences :
    · Swagger/OpenAPI ne documente pas les paramètres attendus
    · Un champ manquant produit une erreur dans la logique métier
      plutôt qu'un 422 Unprocessable Entity propre
    · Les types ne sont pas validés

6. Objet scope imbriqué vs champs plats — incohérence
──────────────────────────────────────────────────────
  resource_mapper.py retourne :
    "scope": {"audience": ..., "violence": ..., "anonymous": ...}

MISE EN PRODUCTION — ANALYSE EXPERT PROJET IA
Rédigée par : GitHub Copilot (expert projet IA / production)
Date : 19 février 2026
═══════════════════════════════════════════════════════════════

  Ce projet a les caractéristiques d'un backend IA en fin de
  phase prototype : la logique est solide, mais plusieurs
  hypothèses de développement sont incompatibles avec une mise
  en production réelle. Voici les interventions par ordre
  de criticité.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
P0 — BLOQUANTS ABSOLUS (ne pas déployer sans corriger)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. Sécurité : CORS et token de développement exposés
  ────────────────────────────────────────────────────
  Dans admin_api.py :
    allow_origins=["*"]        ← n'importe quel domaine peut appeler l'API
    ADMIN_TOKEN_DEV            ← token lisible dans constants.py (versionné Git ?)

  En production :
    · CORS restreint aux domaines autorisés (frontend uniquement)
    · Token admin via variable d'environnement uniquement,
      jamais dans le code source
    · Ajouter ADMIN_TOKEN au .env et s'assurer que .env est dans .gitignore

  2. Serveur lancé en mode --reload (développement)
  ──────────────────────────────────────────────────
  start_server.sh :
    uvicorn admin_api:app --reload ...   ← surveille les fichiers, risque de
                                            redémarrage intempestif

  En production :
    uvicorn admin_api:app --workers 4 --host 0.0.0.0 --port 8000
  Ou mieux : via Gunicorn + Uvicorn workers :
    gunicorn admin_api:app -w 4 -k uvicorn.workers.UvicornWorker

  3. Stockage JSON flat sans isolation des écritures concurrentes
  ───────────────────────────────────────────────────────────────
  working_resources.json (831 lignes) et rag_resources.json sont
  lus/écrits directement sans verrou. Avec plusieurs workers
  (--workers 4), les écritures simultanées corrompent le fichier.

  Solution minimale : asyncio.Lock() ou threading.Lock() dans
  workflow_manager.py autour de _save_json().

  Solution pérenne : migrer vers SQLite (stdlib Python, zéro
  dépendance) ou PostgreSQL si accès concurrent élevé attendu.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
P1 — RISQUES OPÉRATIONNELS (déploiement fragile sans cela)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  4. Appels LLM synchrones dans des endpoints async
  ──────────────────────────────────────────────────
  OpenRouterClient._make_request() utilise requests.post()
  (bibliothèque synchrone) à l'intérieur d'un handler FastAPI
  async. Cela bloque l'event loop le temps de la requête HTTP
  vers OpenRouter, rendant le serveur non réactif pour tous
  les autres appels pendant ce laps de temps.

  Correction :
    · Remplacer requests.post par aiohttp.ClientSession.post()
      (déjà dans requirements.txt — c'est la bonne dépendance)
    · Ou utiliser asyncio.to_thread() comme solution minimale :
        response = await asyncio.to_thread(requests.post, ...)

  5. Aucune limite de débit sur les endpoints LLM
  ─────────────────────────────────────────────────
  POST /discover-by-category/{category} peut être appelé en boucle
  sans restriction. Une seule découverte peut coûter plusieurs
  appels LLM. Sans rate limiting, le quota API (Gemini/OpenRouter)
  peut être épuisé en quelques minutes.

  Solution minimale : slowapi (compatible FastAPI/Starlette) :
    limiter = Limiter(key_func=get_remote_address)
    @router.post("/discover-by-category/{category}")
    @limiter.limit("10/minute")

  6. Pas de gestion de l'épuisement du quota LLM
  ─────────────────────────────────────────────────
  LLMManager._stats comptabilise les appels en mémoire, mais
  les stats sont perdues au redémarrage et aucune alerte n'existe
  si le quota est épuisé. En production, un appel LLM qui échoue
  silencieusement donne l'impression que la découverte "tourne"
  sans jamais retourner de ressources.

  Interventions :
    · Persister les stats LLM dans un fichier JSON ou une table
    · Ajouter un endpoint GET /admin/llm/stats exposant provider,
      total_calls, success_rate, last_error
    · Exposer le quota restant via l'endpoint /health (GET /health
      actuel ne teste pas la connexion LLM)

  7. Pas de processus superviseur en cas de crash
  ─────────────────────────────────────────────────
  Si uvicorn crashe, le service est mort jusqu'à redémarrage manuel.

  Solution selon l'infrastructure :
    · Systemd service unit (Linux bare metal)
    · Docker + restart: always (containerisation)
    · PM2 (si l'infra est déjà Node.js)

  8. Sauvegarde des données JSON absente
  ───────────────────────────────────────
  working_resources.json contient l'ensemble des ressources
  validées. Il n'existe aucune stratégie de backup. Une écriture
  corrompue ou une suppression accidentelle efface tout le travail
  de découverte et de validation.

  Minimum viable :
    · Cron quotidien : cp working_resources.json backups/$(date +%Y%m%d).json
    · Conserver 30 jours de backups


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
P2 — OBSERVABILITÉ (qualifier les incidents en production)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  9. Logs non structurés
  ───────────────────────
  Les logs (backend.log, server.log) sont des chaînes libres.
  En production, un agrégateur de logs (Loki, CloudWatch, etc.)
  ne peut pas filtrer ou alerter sur des champs non structurés.

  Migration vers JSON logging en 5 lignes :
    import logging, json
    class JsonFormatter(logging.Formatter):
        def format(self, record):
            return json.dumps({"level": record.levelname,
                               "msg": record.getMessage(),
                               "ts": self.formatTime(record)})

  10. Endpoint /health insuffisant
  ─────────────────────────────────
  GET /health retourne uniquement {"status": "healthy"} sans
  vérifier l'état des dépendances réelles.

  Un health check production doit tester :
    · Lecture/écriture working_resources.json → {storage: "ok"}
    · Connexion LLM (test_connection léger) → {llm: "ok" | "degraded"}
    · Mémoire/espace disque si pertinent

  Cela permet à un load balancer ou à Kubernetes de sortir le
  pod de la rotation si le LLM est indisponible.

  11. Aucune traçabilité des coûts LLM
  ──────────────────────────────────────
  tokens_used est capturé dans LLMResponse mais jamais agrégé
  ni loggé. Sur un projet IA, le suivi des coûts est une
  exigence opérationnelle de base.

  Minimum :
    · Logger tokens_used + provider + endpoint dans chaque appel
    · Rapport hebdomadaire via GET /admin/llm/usage-report


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
P3 — QUALITÉ & MAINTENABILITÉ (dette technique à planifier)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  12. Tests d'intégration uniquement, pas de tests unitaires
  ───────────────────────────────────────────────────────────
  Le dossier tests/ contient 6 fichiers qui appellent l'API
  via requests (serveur doit tourner). Il n'existe aucun test
  unitaire avec mocking du LLM ni du workflow_manager.

  Conséquence : impossible de valider un changement sans démarrer
  le serveur et dépenser du quota LLM.

  Priorité : tests unitaires sur resource_mapper.py et
  category_prompts.py (logique pure, sans dépendances externes).

  13. config.json duplique constants.py
  ───────────────────────────────────────
  La liste des pays et langues existe dans constants.py (code)
  ET dans config.json (fichier). Les deux divergent déjà
  (config.json a une structure "languages" imbriquée, constants.py
  a COUNTRIES_CONFIG à plat).

  Source unique recommandée : config.json chargé au démarrage
  dans constants.py via json.load() — le fichier devient
  l'unique référence, modifiable sans recodage.

  14. Singleton LLMManager non thread-safe
  ─────────────────────────────────────────
  get_llm_manager() utilise un global _default_llm_manager.
  Avec plusieurs workers, chaque worker crée son propre singleton
  en mémoire. switch_provider() modifie l'état global partagé
  en cours d'exécution, ce qui peut provoquer des appels avec
  le mauvais provider sur les requêtes concurrentes.

  Correction : instancier LLMManager dans le lifespan FastAPI
  et l'injecter via Depends() plutôt que via un global.

Principe directeur
──────────────────
  Le backend V2 est rétrocompatible : les ressources V1 qui n'ont
  pas les nouveaux champs retournent des valeurs vides ("", false).
  Le frontend doit donc afficher les nouveaux champs de façon
  conditionnelle (si le champ est non vide / non false).

  Ordre absolu des étapes : contrat de données → composant de base
  → pages → hooks. Ne jamais modifier une page avant que les types
  et le composant de base soient à jour.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   Points positifs
   ───────────────
   ✔ Le refactoring en routers est la bonne décision : FastAPI est
     conçu pour cette architecture. Chaque router est testable
     indépendamment et lisible en moins de 300 lignes.

   ✔ La centralisation du mapping dans resource_mapper.py élimine
     une source réelle de bugs (les deux versions divergeaient déjà
     entre les lignes ~940 et ~1115 du monolithe).

   ✔ La rétrocompatibilité est préservée : le backup du monolithe
     existe, et les alias (contact_urgence → service_support) sont
     en place dans discovery.py.

   Points de vigilance
   ────────────────────
   ⚠ Le paramètre admin_id est hardcodé à "admin_user" dans sources.py
     et admin_ops.py. Il faudra injecter verify_admin_token proprement
     via Depends() dans chaque endpoint quand l'auth sera renforcée.

   ⚠ resource_models.py et category_prompts.py n'ont pas encore été
     mis à jour : les nouvelles ressources découvertes via discovery.py
     (V2) seront stockées sans les champs scope_*, is_governmental,
     action_type. Les données seront valides mais incomplètes jusqu'à
     l'implémentation de l'étape CRITIQUE.

   ⚠ Aucun test unitaire n'existe sur les routers. À terme, chaque
     router devrait avoir son propre test avec TestClient FastAPI.

   Verdict
   ───────
   L'architecture cible est atteinte pour la couche infrastructure
   (routers + service mapper). La V2 est techniquement déployable :
   les anciens endpoints sont entièrement préservés dans les routers.
   La prochaine priorité absolue est la mise à jour des modèles et
   des prompts, qui sont le cœur fonctionnel de la V2.
